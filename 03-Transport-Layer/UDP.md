### 1. 定义与核心哲学（UDP为什么存在？）

-   **全称**：User Datagram Protocol（用户数据报协议）。
-   **OSI层级**：传输层（第4层），与TCP平级。
-   **核心哲学**：**最大努力交付（Best-Effort）** + **无状态**。
-   **设计初衷**：TCP为了保证可靠，引入了复杂的确认、重传、拥塞控制机制，导致**头部开销大**、**延迟高**。UDP砍掉了所有可靠性逻辑，换来了**极低延迟**和**极简头部**。适合那些**宁可丢帧也不能等**的场景，比如实时语音、视频直播、DNS查询。

---

### 2. 底层基石：UDP报文头（极致简约，仅8字节）

把TCP那20~60字节的复杂头部忘掉，UDP的头部只有**固定的8个字节**，分为4个字段，每个字段占2字节（16位）：

| 偏移量 (bits) | 字段名 | 含义与底层细节 |
| :--- | :--- | :--- |
| 0 - 15 | **Source Port** | 源端口（可选，若不需要回复则填0）。 |
| 16 - 31 | **Destination Port** | 目的端口。**核心路由依据**。 |
| 32 - 47 | **Length** | **UDP头部 + UDP数据**的总长度（单位为字节）。最小值是8（即无数据的情况）。 |
| 48 - 63 | **Checksum** | **校验和**。计算覆盖了伪头部（Pseudo Header，包含源IP、目的IP、协议号、UDP长度）+ UDP头部 + 数据。 |

**关键工程细节**：
-   **没有序列号（SEQ）**：所以无法排序，乱序到达的应用层必须自己处理顺序。
-   **没有确认号（ACK）**：发完就忘，根本不管对方收没收到。
-   **没有窗口大小**：没有流量控制和拥塞控制。发送端可以瞬间把网络带宽打满，**这也是UDP是DDoS放大器根本原因**。

> **抓包冷知识**：在Wireshark中过滤UDP流量，直接用 `udp` 即可。如果看到 `udp.checksum == 0`，这是因为网卡开启了 **TCP/UDP 校验和卸载（Checksum Offload）**，Wireshark抓到的包在计算校验和之前就被截获了，显示为0x0000，这**不是错误**，而是硬件加速导致的“假象”，不影响线上传输。

### 3. 工作机制（UDP的“三无”特性）

1.  **无连接**：发送数据前**不需要**三次握手。应用程序随时可以调用 `sendto()` 将数据扔进网络栈。
2.  **无状态**：内核不会为UDP通信维护任何连接表（不像TCP有 `ESTABLISHED`、`TIME_WAIT` 状态）。服务端重启后，客户端不知道，继续发数据，服务端只会收到ICMP端口不可达，但客户端不感知。
3.  **无可靠保证**：数据包在途中可能被路由器丢弃（TTL超时），也可能被接收端网卡丢弃（缓冲区满）。UDP协议栈**不会重传**，也不会通知发送方“你的包丢了”（除非开启了ICMP源站抑制，但现代系统基本关闭）。

### 4. 典型应用与端口映射（内网渗透必背）

| 端口 (Port) | 协议 | 应用场景 | 红队/内网关注点 |
| :--- | :--- | :--- | :--- |
| **53** | DNS | 域名解析 | **DNS隧道（dnscat2）**、DNS劫持、区域传输（AXFR）。 |
| **67/68** | DHCP | 动态主机配置 | DHCP Starvation（饿死攻击）、伪造DHCP Server劫持网关。 |
| **69** | TFTP | 简单文件传输 | 无认证，常用于网络设备（交换机/路由器）的配置文件下载，内网信息收集重点。 |
| **123** | NTP | 网络时间同步 | **NTP放大攻击**（monlist命令）、时间同步欺骗（Kerberos依赖时间，偏差过大会导致认证失败）。 |
| **137/138** | NetBIOS | Windows名称解析与数据报服务 | **NetBIOS名称欺骗**、**LLMNR/NBT-NS投毒（Responder工具）**——内网获取NTLM哈希的经典入口。 |
| **161/162** | SNMP | 简单网络管理协议 | SNMP Community（默认public/private）泄露，可获取设备全量配置信息。 |
| **514** | Syslog | 日志传输 | 日志窃听或伪造日志注入。 |
| **5353** | mDNS | 多播DNS（苹果/Linux） | 与LLMNR类似，可用于本地链路欺骗。 |

### 5. 安全视角：UDP是攻击者的“最佳好友”

UDP的无状态特性，使得它成为网络攻击中最趁手的武器。

#### A. 反射放大攻击（Reflection & Amplification DDoS）
这是UDP最臭名昭著的安全问题。
-   **原理**：攻击者将**源IP地址伪造（Spoofing）**成受害者的IP，向大量的UDP公共服务（NTP、DNS、Memcached、CLDAP）发送一个极小的查询包。
-   **放大**：服务端收到查询后，向“受害者”（伪造的源IP）发送一个巨大的响应包。
-   **放大倍数**：DNS的放大倍数可达50~70倍，Memcached曾达到夸张的**5万倍**。
-   **防御**：ISP层面启用**单播反向路径转发（uRPF）**防止源IP伪造，或关闭不必要的UDP公开服务。

#### B. UDP端口扫描（内网横向探测的难点）
-   由于UDP无连接，扫描UDP端口非常慢且不可靠。发送一个UDP包给关闭的端口，对方大概率会回复一个 **ICMP Type 3 Code 3（端口不可达）**；如果端口开放，对方**可能不回复任何内容**（因为应用层协议没收到完整请求，直接丢弃）。
-   **实战命令**：使用 `nmap -sU -p 53,137,161 --top-ports 100 <target>`。**注意**：UDP扫描极慢（因为要等待ICMP超时），且容易丢包，建议在非业务高峰期进行。

#### C. 内网投毒（LLMNR / NBT-NS 欺骗）
这是你在内网AD域中**必须精通**的攻击。
-   **场景**：Windows主机在DNS解析失败后，会通过UDP 5355（LLMNR）或UDP 137（NetBIOS）向本地子网广播：“谁是文件服务器？”
-   **攻击**：攻击者运行 **Responder** 工具，监听UDP广播，回复“我是文件服务器，但需要先认证（发NTLM Hash过来）”。
-   **后果**：受害主机会将用户的NTLM哈希发过来，攻击者可以离线破解或进行**NTLM中继攻击**，直接拿下域控。

### 6. UDP与TCP的本质区别总结（实战对比表）

| 对比维度 | TCP | UDP |
| :--- | :--- | :--- |
| **头部大小** | 20~60 字节（携带大量控制信息） | **固定 8 字节**（轻如鸿毛） |
| **传输单位** | **字节流（Stream）**，无边界，需应用层自行分包 | **数据报（Datagram）**，有明确边界，一次`recvfrom`收一个完整的报 |
| **连接状态** | 面向连接（有状态） | **无连接（无状态）** |
| **可靠性** | 可靠，有序，无重复 | **尽最大努力，可能丢、乱、重** |
| **流量/拥塞控制** | 有（滑动窗口、慢启动） | **无**（发爆网卡为止） |
| **适用场景** | HTTP/HTTPS、SSH、SMTP、文件传输 | **DNS查询、实时音视频（WebRTC/RTP）、游戏、SNMP、DHCP** |
| **防火墙穿透** | 状态检测防火墙容易跟踪（有状态） | 防火墙难以跟踪（无状态），需额外配置规则或开启ALG（应用层网关） |

### 7. 实战抓包分析（tcpdump + Wireshark）

**需求**：排查内网是否有主机在进行异常的DNS放大攻击外联。

```bash
# 在网关服务器上抓取UDP 53端口的大包（正常DNS响应不超过512字节，放大攻击包通常>1400字节）
sudo tcpdump -i eth0 -nn 'udp dst port 53 and length > 800' -c 100 -w suspicious_dns.pcap
```
-   将抓到的包拖入Wireshark，过滤 `dns.flags.response == 1`，观察 `udp.length` 字段，如果看到大量响应包长度在 3000~4000 字节，且 `Queries` 请求极小，基本可以判定为反射攻击。

### 8. 老工程师的UDP避坑指南（工程经验）

1.  **MTU（最大传输单元）陷阱**：以太网MTU通常1500字节。UDP数据报如果超过1472字节（1500 - IP头20 - UDP头8），IP层就会**分片（Fragmentation）**。只要丢失一个分片，整个UDP包就废了。**最佳实践**：在内网复杂链路中，强制控制UDP应用层数据小于1400字节，避免分片带来的丢包风险。
2.  **缓冲区溢出**：UDP接收端如果处理速度跟不上接收速度，内核的Socket接收缓冲区会满，新来的包**直接丢弃**。`netstat -su` 可以看到 `packet receive errors`。排查时需调大内核参数 `net.core.rmem_max`。
3.  **防火墙处理**：很多企业边界防火墙默认**丢弃所有入站UDP包**（除了DNS 53）。在内网渗透中，如果你搭建C2隧道，优先考虑**DNS over HTTPS (DoH)** 或 TCP隧道，因为纯净的UDP外联极易被边界ACL拦截。

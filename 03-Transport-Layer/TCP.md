# TCP协议深度解析：从三次握手原理到内网渗透攻击实战

> **文档定位**：本文档面向内网安全与红蓝对抗方向，从TCP协议在传输层的核心职责出发，逐层深入到报文结构、连接管理、可靠性机制、拥塞控制演进及攻击面利用，旨在构建完整的“TCP协议攻防知识闭环”。


## 一、定义与核心矛盾（TCP到底解决了什么）

- **定义**：TCP（传输控制协议）是传输层面向连接的、可靠的、基于**字节流**的协议。
- **底层矛盾**：TCP的“老板”是IP层（网络层）。IP层提供的是 **“Best-Effort（尽力而为）”** 服务——它不保证送达，不保证顺序，不保证不重复。
- **TCP的职责**：TCP是IP层的“快递理赔专员”。它必须解决三个硬核问题：
  1. **怎么确认对方活着且愿意收件？**（连接建立）
  2. **数据发出去，怎么确认对方真的收到了？**（可靠性 + 重传）
  3. **网络太堵或者对方收件太慢，怎么控制发货速度？**（流量控制 + 拥塞控制）


## 二、底层基石：TCP报文头（灵魂在于“编号”）

TCP不是“包”协议，而是**“流”协议**。它不管你应用层一次发了多大一块数据（如一个HTTP POST请求），它都会把这个数据切成一堆**字节**，然后给每个字节编一个“门牌号”。

**必须死磕的三个核心字段（其余都是辅助）：**

| 字段 | 大小 | 含义 | 攻防意义 |
| :--- | :--- | :--- | :--- |
| **Sequence Number（SEQ）** | 32位 | **本报文段所携带数据的第一个字节的编号**。不是“第几个包”，而是**“第几个字节”**。 | 序列号可预测性是会话劫持的根源。现代OS已随机化ISN（初始序列号）。 |
| **Acknowledgment Number（ACK）** | 32位 | **“我期待你下次发给我的第一个字节的编号”**。 | 累积确认机制，用于判断丢包和重传。 |
| **Flags（标志位）** | 9位 | 连接管理的“控制开关”：**SYN**、**ACK**、**FIN**、**RST**、PSH、URG。 | SYN Flood利用SYN位耗尽资源；RST攻击利用伪造RST断连。 |
| **Window Size（窗口）** | 16位 | 接收方告知发送方“我还能收多少字节”。 | 窗口缩放（RFC 1323）可将窗口扩展至1GB，被红队用于高速隐蔽传输。 |
| **Checksum（校验和）** | 16位 | 覆盖**伪头部（含源IP/目的IP/协议号）+ TCP头 + 数据**。 | NAT网关改IP后必须重算TCP校验和，这是NAT消耗CPU的主因之一。 |

> **抓包冷知识**：你在Wireshark里看到的 `Seq=0, Ack=0` 通常是**相对值（Relative Sequence）**，这是Wireshark帮你算的“偏移量”，方便阅读。实际线上传输的是**绝对值（32位随机数）**，这是为了防止攻击者猜测序列号的防御设计。


## 三、连接建立（三次握手）——为什么不是两次或四次？

三次握手的本质是**双向序列号同步**。

- **第一次（SYN, Seq=x）**：客户端说“我要连你，我的起始编号是x”。客户端进入 **`SYN_SENT`**。
- **第二次（SYN+ACK, Seq=y, Ack=x+1）**：服务端说“我听到了，我的起始编号是y，我确认收到了你的x”。服务端进入 **`SYN_RCVD`**。
- **第三次（ACK, Ack=y+1）**：客户端说“我确认收到了你的y”。双方进入 **`ESTABLISHED`**。

**为什么必须是三次（重点：防止历史连接）？**

想象一个场景：客户端发了一个SYN（seq=100）请求建连，但网络卡住了，客户端超时重传了一个新的SYN（seq=200）。结果旧的SYN（seq=100）在网络里绕了一圈后，**比新SYN更晚**到达服务端。

- 如果是**两次握手**：服务端收到旧SYN（seq=100）就会直接建立连接，分配资源，发回ACK。但客户端此时用的明明是新连接（seq=200），收到这个ACK后会直接丢弃（序号不匹配）。服务端却傻傻等数据，浪费资源。
- 如果是**三次握手**：客户端在收到服务端对旧SYN（seq=100）的SYN+ACK时，发现这个ACK确认的不是自己当前的seq（200），于是**发送RST（复位）包**断掉这个历史连接。只有第三次握手（ACK）完成，双向序列号才最终确认同步。


## 四、可靠性传输与窗口机制

### 4.1 流量控制（Flow Control）—— 接收方主导

- **定义**：由**接收方**通过ACK包中的`Window Size`字段告知发送方“我还能收多少字节”。这是**接收方主导**的背压机制。
- **机制**：接收方在每次ACK中携带`Window Size`，发送方必须确保**在途数据（已发未确认）≤ 接收方通告的窗口**。
- **零窗口（Zero Window）**：若接收方窗口为0，发送方停止发送，并周期发送**零窗口探测包（1字节数据）**，询问窗口是否恢复。

### 4.2 拥塞控制（Congestion Control）—— 发送方主导

- **定义**：由**发送方**自己维护一个**拥塞窗口（cwnd）**，根据网络状况（丢包、延迟）动态调整。这是**发送方主导**的自我保护机制。
- **最终发送窗口** = `min(接收方通告的窗口, 发送方维护的cwnd)`。**两者共同决定发送速度，缺一不可。**

### 4.3 拥塞控制的现代演进（必读！）

你的原文只写了慢启动和快速恢复（TCP Tahoe/Reno时代的模型），现代Linux内核已进化：

- **CUBIC（Linux默认）**：不再采用“线性增长+丢包砍半”的锯齿形。使用**三次函数**计算cwnd增长，接近网络容量时增长放缓，丢包后回退到历史高水位的某个比例而非直接砍半。在高带宽、长延迟网络（如跨国专线）中性能远优于旧算法。
- **BBR（Google开发）**：不再依赖丢包作为拥塞信号，而是通过测量**瓶颈带宽**和**最小RTT**主动控制发送速率。已在YouTube和Google全球骨干网大规模部署。
- **红队视角**：攻击者可构造带有特定ECN（显式拥塞通知）标志的包，干扰某些防火墙的ECN降级策略，从而影响BBR的带宽估算，实现低速拒绝服务。

### 4.4 超时重传与快速重传

- **超时重传（RTO）**：TCP估算网络往返时间（RTT）。若一个包发出后过了RTO还未收到ACK，则重传。
- **快速重传（Fast Retransmit）**：若接收方收到乱序包，会重复ACK（如`ACK=101`）。发送方收到**3个重复ACK**时，立即重传缺失的包，无需等待超时。
- **累积确认（Cumulative ACK）**：`ACK=1100`表示“1000~1099都收到了，请从1100开始发”。


## 五、连接关闭（四次挥手）与 TIME_WAIT 陷阱

- **第一次（FIN）**：主动方说“我没数据发了，想关”。
- **第二次（ACK）**：被动方说“收到，但我可能还有数据要发”。
- **第三次（FIN）**：被动方也说“我也没数据了”。
- **第四次（ACK）**：主动方确认收到FIN，进入 **`TIME_WAIT`**。

**为什么主动方必须等 2MSL（通常1~2分钟）？**

最后一次ACK发给被动方后，被动方可能没收到（ACK丢了），会重发FIN。如果主动方直接关闭，就收不到这个重发的FIN，被动方永远卡在`LAST_ACK`状态。所以主动方必须等待 **2MSL（最大报文段寿命的两倍）**，确保这次连接的所有报文段都在网络中消失，才能安全关闭。

**生产环境痛点与Linux内核调优**

高并发短连接服务器（如Nginx反向代理），主动关闭连接会产生大量`TIME_WAIT`，占用端口（可用端口范围约28232个），导致新连接失败，报错`Cannot assign requested address`。

```bash
# 查看当前TIME_WAIT数量
ss -tan | grep TIME-WAIT | wc -l

# 调优方案（慎用）
net.ipv4.tcp_tw_reuse = 1      # 允许将TIME_WAIT socket用于新连接（仅对出站有效）
net.ipv4.tcp_tw_recycle = 0    # 强烈建议关闭，NAT环境下会引发严重问题
net.ipv4.ip_local_port_range = 1024 65000  # 扩大端口范围
net.ipv4.tcp_max_tw_buckets = 5000      # 超过此值立即销毁（暴力手段）
```

> **红队视角**：攻击者可故意消耗目标服务器的临时端口（如高并发短连接请求），导致业务中断。


## 六、红队/渗透测试视角：TCP的五大攻击面

### 1. SYN Flood（拒绝服务）

- **原理**：攻击者发大量SYN，但不发第三次ACK。服务端的半连接队列被塞满，正常用户无法连接。
- **防御**：开启`net.ipv4.tcp_syncookies = 1`（SYN Cookie）。服务器不为每个SYN分配资源，而是计算一个加密Cookie作为SYN+ACK的seq发回，只有收到合法ACK（Cookie+1）才真正建立连接。

### 2. TCP RST攻击（会话中断）

- **原理**：攻击者猜中目标连接的（源IP、源端口、目的IP、目的端口、当前SEQ）五元组，伪造RST包发给两端，强行掐断连接。
- **现实案例**：早期BGP路由劫持曾利用此手法。

### 3. TCP会话劫持（Session Hijacking）

- **原理**：若初始序列号（ISN）可预测（旧Windows系统），攻击者可伪造ACK包插入恶意数据（如向SSH会话注入`\r\n`指令）。
- **现代防御**：现代OS已实现RFC 1948的随机化ISN算法，预测ISN几乎不可能。

### 4. 端口扫描（内网横向探测）

| 扫描类型 | Nmap参数 | 原理 | 优缺点 |
| :--- | :--- | :--- | :--- |
| **SYN扫描（半开）** | `-sS` | 发SYN，收到SYN+ACK就回RST，不完成握手 | 速度快，应用日志不记录（推荐） |
| **Connect扫描（全连接）** | `-sT` | 完成完整三次握手再断开 | 准确，但会被完整记录 |
| **FIN/Null/Xmas扫描** | `-sF`/`-sN`/`-sX` | 关闭端口必须回RST，开放端口忽略（RFC标准） | 绕过无状态防火墙 |

> **踩坑警告**：某些设备（如嵌入式打印机）的协议栈不响应半开SYN，此时必须改用`-sT`才能发现存活主机。

### 5. 窗口缩放利用 + 零窗口探测隐蔽信道（高级）

- **窗口缩放（Window Scaling, RFC 1323）**：通过`Window Scale`选项将窗口放大（最大可到1GB），在极少的ACK交互中传输大量数据。某些NDR设备若未解析此选项，会低估实际传输量，导致数据外泄告警被绕过。
- **零窗口探测隐蔽信道**：被控主机周期性地向C2发送“零窗口探测”包（看起来像正常的TCP保活），C2在回复中通过`Window Size`字段的微小变化或ACK号的异常偏移携带指令。这种流量在传统防火墙上显得“极其正常”，极难被发现。


## 七、内网协议栈联动（实战映射）

- **SMB横向移动**：依赖TCP 445。若防火墙只允许80/443出站，可用**SSH隧道（端口转发）** 或**SOCKS代理**将445映射到内网目标。
- **Kerberos黄金票据**：依赖TCP/UDP 88。Wireshark过滤`tcp.port == 88`，`Follow TCP Stream`可提取加密的TGT。
- **RDP远程桌面**：依赖TCP 3389。RDP的CredSSP（NLA）在TCP握手完成后继续嵌套TLS/SMB，Wireshark无法直接解析NTLM哈希，需配合`tshark`导出原始流。


## 八、避坑指南与排障经验

### 坑1：Ping通但TCP连不上
- 防火墙禁止了目标端口（如TCP 80），但允许ICMP。用`telnet IP 80`或`nmap -p 80 IP`验证端口连通性。

### 坑2：连接建立后频繁断线
- 检查防火墙的状态表是否超时（某些防火墙默认TCP会话超时60分钟，若业务长连接超过此时间，防火墙会发送RST）。
- 检查NAT网关的`ip_conntrack_max`是否被耗尽（查看`/proc/sys/net/netfilter/nf_conntrack_max`）。

### 坑3：TIME_WAIT导致端口耗尽
- 参考第五节调优方案，或改用长连接（HTTP Keep-Alive）减少短连接数。


## 九、TCP知识坐标系（与已学知识的联动）

你已构建的TCP知识上下文：

- **链路层（MAC/VLAN）**：决定数据帧能否在本地广播域内传输。
- **网络层（IP/ICMP/Routing）**：决定数据包能否跨网段到达目标主机。
- **传输层（TCP，本篇）**：在IP的“不可靠”之上建立“可靠”的字节流通道。
- **即将学习**：应用层协议（HTTP/SMB/Kerberos）。理解TCP的序列号和窗口，就理解了这些应用层攻击的“传输底座”。
